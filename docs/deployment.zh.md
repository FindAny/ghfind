本文档说明 ghfind 的生产部署方式：系统由哪些部分组成，代码如何从提交变成线上版本，各环节有哪些质量与安全保障，出现问题时如何回滚和恢复。文中的流程与配置都已在生产环境实际运行并验证；具体命令与故障处理步骤以 [runbook.md](./runbook.md) 为准。

## 1. 概览

ghfind 是 GitHub 开发者与开源项目的评估平台，生产站点为 <https://ghfind.com>。系统完全运行在 Cloudflare 全球边缘网络上，没有自建服务器，也不依赖其他云平台。

| 特性 | 说明 |
| --- | --- |
| 运行平台 | Cloudflare Workers、D1（SQL 数据库）、R2（对象存储）、Durable Objects、Queues、Containers |
| 发布方式 | 事件驱动：任一代码仓库发布版本后，自动组合三个仓库的最新已验证版本并部署 |
| 质量门禁 | 合并前检查 → 合并后全量测试 → 部署提交再次全量测试 → 部署后冒烟测试 → 失败自动回滚 |
| 可追溯性 | 每次生产部署对应一个公开提交，精确记录三个仓库各自的版本与提交号 |
| 评分透明 | 评分算法开源，任何人都可以核对线上分数所用的评分代码版本 |

## 2. 代码仓库与职责

代码分布在三个 GitHub 仓库中，构建时组装成一个完整的工作区。

| 仓库 | 可见性 | 内容 |
| --- | --- | --- |
| `FindAny/ghfind` | 公开 | 评分模块（TypeScript / Go / Python 三种实现，结果保持一致）、SDK、命令行工具，以及**全部 CI/CD 与部署流水线**（部署中心） |
| `FindAny/ghfind-server` | 私有 | 后端：API、数据采集、数据库迁移、各 Worker、Feed 运行时、运维脚本与内部文档 |
| `FindAny/ghfind-frontend` | 私有 | 前端：Astro 站点、React 组件、多语言文案、静态资源 |

设计要点：

- **单一部署入口**：只有公开仓库持有部署流水线和 Cloudflare 凭据。私有仓库只负责代码与版本发布，不能直接修改生产环境。
- **公开仓库不含私有代码**：部署分支上只有公开代码和一份版本清单（`components.manifest.json`）。私有代码只在构建时临时取用，不会写入公开仓库，也不会出现在公开日志中。
- **路径归属唯一**：每个文件属于哪个仓库，统一由公开仓库的 `.github/compose/components.json` 规定。组装时如果同一文件被两个仓库提供，构建直接失败。

## 3. 生产运行架构

```text
                         ghfind.com
                             │
                      ghfind-router            按路径分发请求
          ┌──────────────────┼──────────────────────┐
     ghfind-web          ghfind-api             ghfind（旧版 Next 应用，逐步迁移中）
     Astro 页面           /api/* 接口             静态资源与尚未迁移的接口
          │                  │
          │                  ├─ D1：核心库、Feed 库    R2：媒体与缓存
          │                  ├─ ghfind-talent：人才匹配报告与职位同步（Workflow）
          └── 读取 D1        └─ ghfind-coord：限流、扫描并发控制、报告任务（Durable Objects）

     Feed 运行时：Cloudflare Containers 中的 Go 服务，由独立的网关控制开放状态
     ghfind-cost-monitor：独立 Worker，每 5 分钟检查 Cloudflare 用量与成本
```

| 环境 | 地址 | 说明 |
| --- | --- | --- |
| 生产 | <https://ghfind.com> | 只能由自动流水线部署 |

开发环境（dev.ghfind.com）与按 PR 部署的预览环境已于 2026-11-09 下线；上线前的检查由各仓库 PR 的 CI 和 `deploy` 分支上的完整测试完成。

## 4. 发布与部署流程

### 4.1 总流程

```text
① 任一仓库：代码合并到 main，CI 通过
② 维护者打版本标签 vX.Y.Z
③ 发布流水线：确认该提交的 CI 确实通过 → 标记为“已验证版本”（rel/vX.Y.Z）
   → 发布 GitHub Release → 立即触发组合（事件驱动，无轮询）
④ 组合：取三个仓库各自最新的已验证版本 → 试组装确认无冲突
   → 生成部署提交（公开代码 + 版本清单）→ 推送到公开仓库的 deploy 分支
⑤ deploy 分支 CI：在完整组装的工作区上运行全量测试
   （应用检查、Feed 存储契约、Feed 运行时构建、端到端测试、发布校验）
⑥ 生产部署：按版本清单精确取回各仓库代码 → 数据库迁移 → 部署 Worker
   → 冒烟测试 → 失败则自动回滚
```

### 4.2 关键机制

| 机制 | 作用 |
| --- | --- |
| 事件驱动 | 版本发布后立即触发组合，没有定时轮询，不存在版本状态不同步的时间窗口。触发失败时发布任务直接报错，不会静默跳过 |
| 串行组合 | 组合任务排队执行。两个仓库几乎同时发布时，后一次组合会同时包含两个新版本 |
| 只向前部署 | 较新的部署提交出现后，较旧的部署会被自动跳过，生产版本只会前进 |
| 精确版本 | 部署时必须读取版本清单，按其中固定的提交号取代码，与 CI 验证的内容逐字节一致 |
| 写保护 | deploy 分支受仓库规则保护，只有组织自有的发布机器人（GitHub App）可以写入，其他账号的推送都会被规则拒绝 |
| 数据库互斥 | 网站发布与应用发布共用同一个互斥组，核心数据库迁移不会并发执行 |

### 4.3 发布顺序规则

公开仓库的流水线会调用后端仓库的脚本，而部署提交使用的是公开仓库**最新已发布版本**中的流水线。因此，如果后端改动删除或改名了流水线依赖的脚本或命令，必须先更新并发布公开仓库，再发布后端，否则部署前的全量测试会失败，生产不会更新（不影响线上运行）。私有仓库的每个 Pull Request 都会自动检查这一点：公开仓库流水线依赖的脚本或命令一旦缺失，PR 检查即失败。

### 4.4 实际耗时（参考）

| 阶段 | 通常耗时 |
| --- | --- |
| 发布验证与组合 | 1–3 分钟（如果 CI 尚未完成，会等待它完成） |
| deploy 分支全量测试 | 约 6–10 分钟 |
| 生产部署（网站） | 约 5 分钟 |
| 生产部署（含 Feed 运行时切换） | 约 15 分钟（包含约 4 分钟的容器生效等待） |

## 5. Feed 运行时的独立发布

Feed（社区信息流）运行在 Cloudflare Containers 中，发布风险高于普通网页。为此，Feed 和网站分开发布：

1. 每次生产发布先计算 Feed 相关输入（容器镜像内容、运行时 Worker、Feed 数据库结构、相关脚本）的哈希值，并与上一次**成功**切换时记录的哈希（`feed/released` 标签）比较。
2. **没有变化**：只发布网站，并保持 Feed 网关当前的开放状态。Feed 运行时完全不动，网站发布既不会意外开放 Feed，也不会意外关闭它。
3. **有变化**：执行完整的 Feed 切换。切换前先等待约 4 分钟，让 Cloudflare 的容器实例全部换成新镜像。这个等待解决了此前大部分 Feed 发布失败（新旧镜像交替期间的版本不一致）。
4. 只有冒烟测试通过的切换才会更新 `feed/released`；失败的切换会在下一次发布时自动重试。

需要时，维护者可以强制执行一次 Feed 切换，也可以在不发布的情况下暂停 Feed（见 runbook 的 `feed` 一节）。

## 6. 数据库变更管理

- 核心数据库（D1）的迁移文件放在私有后端仓库中，按编号顺序执行，原则上只做增量变更（新增表、列、索引）。
- **生产审批清单**：生产部署只执行列在 `ops/feed-production-schema-release.json` 中的迁移，每个文件都附 SHA-256 校验值。迁移文件在审批后被改动的，部署会直接报错（approved migration changed）并停止。新迁移需要单独提交审批，并通过测试后才会进入生产。后端仓库的 PR 检查会核对：每个迁移文件都必须已列入审批清单（少数历史迁移列在冻结的例外名单中），否则检查失败，避免新迁移被生产静默跳过。
- 生产迁移由部署流水线按审批清单执行。Worker 回滚不会回滚数据库，因此破坏性变更（删除、改名）必须分步进行：先上线兼容的新代码，再在后续版本中清理。

## 7. 质量保障

| 阶段 | 检查内容 |
| --- | --- |
| Pull Request | 评分三语言一致性与开源边界、JavaScript SDK、工作流语法与仓库保护策略（必须全部通过才能合并） |
| 合并到 main | 私有仓库：类型检查、代码规范、单元测试、Go 测试、前端构建、公开仓库流水线依赖检查与发布契约测试（含迁移审批核对）；公开仓库：全量测试 |
| 版本发布 | 发布流水线再次确认该提交的 CI 已通过，否则拒绝发布 |
| 部署前 | deploy 分支全量测试；部署流水线核对“该提交的 CI 已成功”的证据，核对不通过则在任何写操作之前停止 |
| 部署后 | 公开冒烟测试（首页、排行榜、个人页、评分 API、徽章、站点地图等）；失败则自动回滚到部署前记录的版本，并再次验证 |
| 运行中 | 成本监控 Worker 每 5 分钟检查用量，异常时告警 |

## 8. 回滚与故障恢复

| 场景 | 处理方式 | 影响 |
| --- | --- | --- |
| 部署后冒烟测试失败 | 流水线自动回滚到部署前的 Worker 版本并复验 | 无需人工介入 |
| 新版本上线后发现问题 | 用旧版本标签重新组合并部署（推荐，走完整质量门禁） | 约 15 分钟 |
| 需要立即止损 | 在 Cloudflare 上把 Worker 回滚到指定版本，秒级生效 | 不回滚数据库 |
| Feed 异常 | 执行 Feed 暂停流程，只关闭 Feed，不影响网站其他功能 | Feed 暂不可用 |
| 发布未能触发组合 | 版本已验证但未部署；维护者手动运行一次组合即可 | 无 |

每次生产部署的 Worker 版本都带有对应部署提交的标记，可以从 Cloudflare 的版本记录追溯到三个仓库的具体代码。

## 9. 安全与合规

- **凭据分级**：Cloudflare 部署凭据和运行时密钥只保存在公开仓库受保护的部署环境中，只有 `main` 和 `deploy` 分支上的流水线能使用；私有仓库不持有任何部署凭据。
- **发布机器人**：组织自有的 GitHub App，只授予读取代码、推送 deploy 分支和触发组合这几项最小权限，每次任务使用短期令牌。只有组织所有者可以管理和更换它的密钥。
- **外部贡献安全**：来自外部的 Pull Request 只运行不需要任何密钥的检查，接触不到凭据；仓库不使用 `pull_request_target`。
- **公开日志**：公开仓库的流水线日志对所有人可见。密钥会被自动遮蔽，流水线也不会输出私有源码或把它上传为构建产物。
- **GitHub 令牌池**：生产扫描使用的 GitHub 访问令牌只存在于私有生产部署中，不会进入任何代码仓库、SDK 或日志。
- **评分可验证**：线上分数全部由公开的 `scoring/` 模块计算。deploy 分支的版本清单记录了当前线上的公开版本，任何人都可以核对。

## 10. 角色与权限

| 角色 | 权限 |
| --- | --- |
| 组织所有者 | 管理仓库、部署环境、发布机器人和 Cloudflare 账号；可以手动组合、固定版本、强制 Feed 切换 |
| 维护者 | 合并代码、打版本标签，从而触发自动部署 |

## 11. 常用操作速查

```sh
# 发布一个版本（在对应仓库的 main 上，CI 通过后）
git tag vX.Y.Z && git push origin vX.Y.Z

# 预览组合结果，不部署
gh workflow run compose-release.yml -R FindAny/ghfind -f dry_run=true

# 回滚：把指定版本重新组合并部署
gh workflow run compose-release.yml -R FindAny/ghfind \
  -f ghfind=vA.B.C -f ghfind_server=vD.E.F -f ghfind_frontend=vG.H.I -f force=true

# 查看当前线上版本清单
git fetch origin deploy && git show origin/deploy:components.manifest.json

# 跟踪某个版本从发布到上线的全过程，并检查线上页面（只读）
.github/compose/release-status.sh --wait ghfind-server vX.Y.Z
.github/compose/probe.sh
```

完整操作（包括恢复流程、密钥轮换和本地开发）见 [runbook.md](./runbook.md)。

## 12. 术语表

| 术语 | 含义 |
| --- | --- |
| 已验证版本 | 带 `rel/vX.Y.Z` 标记的版本，表示该提交的 CI 已通过 |
| 组合（compose） | 把三个仓库的指定版本合成一个部署提交的过程 |
| deploy 分支 | 公开仓库中专门存放部署提交的分支，只有发布机器人能写入 |
| 版本清单 | `components.manifest.json`，记录一次部署中三个仓库各自的版本与提交号 |
| Feed 切换（cutover） | 更新 Feed 容器运行时并切换网关的完整流程 |
| 冒烟测试 | 部署后对线上关键页面与接口做的只读快速检查 |
